# GRE-TUN 12.2.0 — Transparent TCP / IP واقعی مشتری

این نسخه بر پایه مخزن `0fariid0/GRE-TUN`، نسخه 12.1.1 و commit `03d8d22` ساخته شده است. قابلیت Transparent یک حالت اختیاری است. بخش‌های BackPack، تست سرعت و فوروارد معمولی در بسته کامل موجودند.

**ابتدا یک کلاینت آزمایشی را تست کنید؛ این بسته به‌تنهایی هیچ فورواردی را به Transparent منتقل نمی‌کند.**

## نصب روی هر سه سرور

بسته را استخراج کنید، وارد پوشه آن شوید و پیش‌نیازها را نصب کنید:

```bash
sudo apt-get install -y python3 iproute2 iptables conntrack
sudo bash install-local.sh </dev/null
```

نصب محلی فایل‌های مدیر و ماژول را جایگزین می‌کند. برای این قابلیت باید مدیر جدید روی هر سه سرور نصب شود تا محافظت از تنظیمات فعال باشد. هیچ دستور ارتقای سیستم‌عامل یا ریبوتی لازم نیست.

## دستورهای مخصوص سه سرور گزارش‌شده

این دو پروفایل فقط برای آزمایش TCP پورت 2044 آماده‌اند؛ آدرس‌های عمومی در برنامه ثابت نشده‌اند.

| پروفایل | اینترفیس | آدرس ایران | آدرس خارج | پورت اصلی | پورت تست ایران |
|---|---|---|---|---|---|
| ایران اول | wgtun1 | 10.20.1.1 | 10.20.1.2 | 2044 | 12044 |
| ایران دوم | greplus3 | 10.30.3.1 | 10.30.3.2 | 2044 | 12044 |

### ۱. ابتدا خارج، 116.203.167.232 / 91.107.243.71

در پوشه استخراج‌شده اجرا کنید:

```bash
sudo python3 transparent_forward.py outside @profiles/iran1-wg-2044.json
sudo python3 transparent_forward.py outside @profiles/iran2-greplus-2044.json
```

**نکته WireGuard:** پروفایل اول در خارج، AllowedIPs همان peer تک‌نفره ایران را به `0.0.0.0/0` گسترش می‌دهد تا IP واقعی کاربران پذیرفته شود. همزمان `Table = off` در همان فایل گذاشته می‌شود تا wg-quick مسیر پیش‌فرض عمومی نسازد. مسیر برگشت فقط با mark اتصال انتخاب می‌شود. کلیدها، Endpoint و ListenPort حفظ می‌شوند. این کار فقط وقتی خودکار انجام می‌شود که تنظیم پایه یک peer و AllowedIPs دقیقاً `10.20.1.1/32` باشد؛ تنظیم‌های سفارشی برای بازبینی متوقف می‌شوند.

این دو دستور HAProxy یا Xray خارج را restart نمی‌کنند و ورودی‌های پنل را تغییر نمی‌دهند.

### ۲. ایران اول، 109.70.77.5

```bash
sudo python3 transparent_forward.py iran @profiles/iran1-wg-2044.json
```

### ۳. ایران دوم، 188.213.67.220

```bash
sudo python3 transparent_forward.py iran @profiles/iran2-greplus-2044.json
```

در هر ایران، فقط یک listener آزمایشی روی `12044` ساخته می‌شود. فوروارد اصلی `2044` تا مرحله بعد به مسیر قبلی اشاره می‌کند.

### ۴. آزمون واقعی با یک کاربر

از کانفیگ فعلی یک کپی بگیرید. فقط پورت سمت ایران آن کپی را از `2044` به `12044` تغییر دهید. UUID، کلید REALITY/TLS، SNI، transport، path و سایر مقادیر همان قبلی باشند. برای هر ایران جداگانه بررسی کنید:

1. کلاینت به‌درستی متصل شود و وب‌سایت/ترافیک واقعی باز شود.
2. در سرور خارج آدرس TCP مشتری واقعی دیده شود، نه `10.20.1.1` یا `10.30.3.1`:

```bash
sudo ss -ntp 'sport = :2044'
```

3. آدرس را با IP عمومی همان اتصال اینترنت مشتری مقایسه کنید. پشت NAT اپراتور، IP عمومی مشترک اپراتور دیده می‌شود؛ IP خصوصی گوشی قابل بازیابی نیست.
4. اتصال مستقیم و کانفیگ‌های قبلی روی پورت اصلی همچنان کار کنند.

PROXY Protocol را روی Inbound روشن نکنید؛ این روش هدر جدیدی به handshake اضافه نمی‌کند. مشاهده IP در رابط پنل به امکانات و فعال‌بودن ثبت اتصال در همان نسخه پنل بستگی دارد؛ تغییرات این بسته در شبکه و HAProxy انجام می‌شود.

### ۵. انتقال کاربران پس از آزمون موفق

فقط پس از آزمون بالا، در ایران اول اجرا کنید:

```bash
sudo python3 transparent_forward.py promote 87f1ccf2408e
```

در ایران دوم:

```bash
sudo python3 transparent_forward.py promote e169a0147fef
```

پورت عمومی کاربران همان `2044` می‌ماند. promote، backend اتصال‌های جدید را تغییر می‌دهد و از reload استفاده می‌کند؛ restart جایگزین reload نمی‌شود. اتصال‌های قبلی در worker قبلی ادامه می‌یابند تا بسته شوند. وجود `hard-stop-after` یا سرویس بدون graceful reload مانع فعال‌سازی خودکار است. با این حال «صفر قطعی در همه سرورها» بدون تست زنده قابل تضمین نیست.

## برگشت و حذف تدریجی

**ابتدا ایران؛ بعد خارج.** شناسه همان پروفایل است. برای مثال در ایران اول:

```bash
sudo python3 transparent_forward.py drain 87f1ccf2408e
sudo python3 transparent_forward.py cleanup 87f1ccf2408e
```

`drain` اتصال‌های جدید را به backend قدیمی برمی‌گرداند و listener آزمایشی را حذف می‌کند. مسیر برگشت اتصال‌های در حال کار باقی می‌ماند. اگر `cleanup` تعداد اتصال باقی‌مانده را نشان داد، صبر کنید و بعد دوباره آن را اجرا کنید. TIME_WAIT ممکن است مدتی در conntrack باقی بماند. هیچ flush عمومی conntrack اجرا نمی‌شود.

پس از پاک‌سازی همین پروفایل در ایران، همان دو دستور را برای همان شناسه در خارج اجرا کنید. برای ایران دوم، شناسه `e169a0147fef` است. خارج، تنظیم اولیه WireGuard و rp_filter را فقط پس از پایان آخرین پروفایل مشترک همان اینترفیس بازمی‌گرداند. فایل‌های پشتیبان در `/etc/gretun-transparent` حفظ می‌شوند.

## سرورهای دیگر و پورت‌های دیگر

روی ایران، مدیر جدید را باز کنید:

```bash
sudo bash /usr/local/bin/gretun-manager.sh
```

از منوی HAProxy گزینه **۹ — transparent client IP** را بزنید. گزینه ۱ ماژول، بدون تغییر شبکه یک plan می‌سازد: انتخاب اینترفیس، انتخاب فوروارد TCP، آدرس داخلی خارج و پورت آزمایشی. token نمایش داده می‌شود. همان token را ابتدا در خارج با گزینه ۲، سپس در ایران با گزینه ۳ آماده کنید. گزینه ۴ انتقال پس از آزمون، گزینه ۵ وضعیت و گزینه‌های ۶/۷ برگشت و پاک‌سازی هستند.

خارج برای این قابلیت نیاز به نصب HAProxy ندارد؛ ماژول را مستقیم باز کنید:

```bash
sudo python3 /usr/local/lib/gretun/transparent_forward.py menu
```

توکن یک برنامه تنظیمات است، نه رسید موفقیت سرور مقابل یا رمز احراز هویت. اجرای آن باید فقط توسط مدیر سرور انجام شود.

## دامنه پشتیبانی و توقف‌های ایمن

- Linux با systemd، IPv4 و HAProxy در حالت TCP. نسخه‌های 2.4 و 2.8 از نظر parsing بررسی شده‌اند.
- GRE/GRE Plus مسیریابی‌شده؛ WireGuard با یک peer و تنظیم پایه ساده. WireGuard چند peer، AllowedIPs سفارشی، hook و SaveConfig خودکار نیازمند بازبینی‌اند.
- HAProxy با workerهای root و مجوزهای شبکه لازم. برنامه کاربر سرویس را به root تغییر نمی‌دهد؛ سرویس سخت‌سازی‌شده بدون قابلیت لازم متوقف می‌شود.
- listener ساده IPv4 و یک backend plain TCP از الگوی فعلی مدیر. TLS termination در HAProxy، server options سفارشی، ACL مسیریابی، ورودی IPv6 و فوروارد mode http خودکار تغییر نمی‌کنند.
- در خروجی شما `2095` و `8080` از نوع mode http هستند و در این نسخه برای Transparent انتخاب نمی‌شوند. TCP پورت `2044` برای آزمایش آماده شده است.
- UDP companion فعلی به روش سابق کار می‌کند؛ این قابلیت IP مبدأ را فقط برای اتصال TCP منتقل می‌کند.
- BackPack فعلاً برای Transparent انتخاب نمی‌شود؛ قابلیت تونل و فوروارد عادی BackPack حفظ شده است.
- محیط فاقد CAP_NET_ADMIN/CAP_NET_RAW، نبود conntrack، تداخل mark یا جدول، peer اشتباه و رابط down با خطا متوقف می‌شوند. روی هر چیدمان دلخواه، کارکرد خودکار تضمین نمی‌شود.
- فقط rp_filter همان رابط به حالت loose تغییر می‌کند. جدول main، gateway عمومی، SSH، کلیدهای WireGuard و تنظیمات Xray برای این قابلیت بازنویسی نمی‌شوند.
- تا وقتی پروفایل باقی است، مدیر جلوی بازسازی HAProxy و ویرایش/حذف تونل مربوطه یا reset همه را می‌گیرد؛ ابتدا drain/cleanup کنید. ویرایش دستی بیرون از مدیر تحت این محافظت نیست.
- اگر firewall توسط ابزار دیگری از نو ساخته شود، از دستور `restore` برای اعمال دوباره قوانین همین ماژول استفاده کنید. تداخل با تغییرات بیرون از مدیر همچنان به بازبینی نیاز دارد.
- اگر وضعیت `preparing` یا `recovery-needed` دیدید، خروجی خطا و status را بررسی کنید و فایل پروفایل/بکاپ را کورکورانه حذف نکنید. restore پروفایل‌های سالم دیگر را ادامه می‌دهد، ولی پروفایل ناقص را خودکار فعال نمی‌کند.

## بررسی وضعیت

```bash
sudo python3 /usr/local/lib/gretun/transparent_forward.py status
sudo systemctl status gretun-transparent.service --no-pager
```

قوانین در زمان آماده‌سازی همان لحظه اعمال می‌شوند. برای WireGuard یک ExecStartPost اختصاصی هم اضافه می‌شود تا بعد از شروع دوباره همان رابط، مسیر برگشت بازسازی شود. تعمیر GRE/GRE Plus در مدیر نیز hook بازسازی مسیر دارد. سرویس restore برای بوت فعال می‌شود؛ ممکن است تا ریبوت یا اجرای دستی در وضعیت inactive باشد. سرویس restore مسیرهای ذخیره‌شده را بازسازی می‌کند و HAProxy را restart نمی‌کند.
